# Project Prompt: Natural Language AI Resume Creator — Anthropic Claude-Powered Resume Builder

## 1. Project Overview

Build a complete, working full-stack web application called **AI Resume Creator**.

The application allows users to create professional, job-specific resumes by describing their requirements in natural language and answering questions asked by an AI assistant.

The application must not be a basic resume template website or a standalone chatbot. It must provide an interactive, guided resume-building workflow where users can explain their background, answer follow-up questions, generate a complete resume, edit every section, preview the final document and download it as a PDF.

Use the Anthropic Claude API for AI-powered resume generation, content improvement, job-description analysis and suggestions.

### Main user workflow

1. The user opens the website and selects **Create My Resume**.
2. The AI asks what type of job or role the user is applying for.
3. The user describes their requirements in natural language, for example:
   - "Create a resume for an entry-level AWS Data Engineer job in Singapore."
   - "I am a final-year computer science student with internship experience and IoT projects."
   - "Make my resume ATS-friendly and highlight my technical skills."
4. The AI asks relevant follow-up questions about education, work experience, projects, technical skills, certifications, achievements and contact information.
5. The user answers in normal conversational language.
6. The AI organizes the answers and generates a complete professional resume.
7. The user reviews the resume in a live preview and edits any section manually.
8. The user can ask AI to improve selected sections without regenerating the entire resume.
9. The user chooses a resume template and downloads the final resume as a PDF.
10. The user can open the AI API Usage dashboard to inspect the API usage generated by this application.

The application must request missing information instead of inventing qualifications, employment history, education, dates, certifications or achievements.

## 5. Natural Language Resume Interview

Implement a conversational resume-building assistant.

The user must be able to communicate normally instead of filling in a long, rigid form before getting started.

### Initial questions

Start with a few essential questions:

1. What job title or type of role are you targeting?
2. Are you applying as a fresher, student, experienced professional or career changer?
3. Do you have an existing resume or are you creating one from scratch?
4. Is there a particular job description you want to target?

Allow users to answer these questions in one natural-language message.

Do not force users to answer every question individually if they have already provided the information.

### Dynamic follow-up questions

Based on the user's answers, ask only the relevant missing questions.

For example:

- If the user is a fresher, focus on education, projects, internships, certifications and skills.
- If the user has work experience, ask about responsibilities, technologies, measurable outcomes and achievements.
- If the user is changing careers, identify transferable skills and relevant projects.
- If the user supplies a job description, identify relevant keywords and compare them with the user's actual qualifications.
- If the user has an existing resume, allow them to paste its contents or upload a supported document if file upload is implemented.

Ask one manageable group of questions at a time. Avoid overwhelming users with a large questionnaire.

### Resume information to collect

Support the following sections:

- Full name.
- Contact information.
- Professional summary.
- Target job title.
- Work experience.
- Internships.
- Education.
- Technical skills.
- Soft skills.
- Projects.
- Certifications.
- Achievements.
- Publications, if relevant.
- Volunteer experience, if relevant.
- Languages, if relevant.
- Portfolio, GitHub and LinkedIn links.
- Additional sections requested by the user.

Allow optional sections to be skipped or removed.

### Conversation state

Maintain a structured resume data object throughout the interview.

Example:

```js
const resume = {
  personalInfo: {
    fullName: "",
    email: "",
    phone: "",
    location: "",
    linkedin: "",
    github: "",
    portfolio: ""
  },
  targetRole: "",
  professionalSummary: "",
  skills: [],
  experience: [],
  education: [],
  projects: [],
  certifications: [],
  achievements: [],
  additionalSections: []
};
```

This is a starting structure. Extend it when necessary, while keeping the data model consistent between the AI service, editor, preview and PDF generator.

The AI must update this structured data rather than returning only a block of unstructured text.

### Handling missing information

- Do not invent personal details.
- Do not fabricate experience or job titles.
- Do not invent certifications, academic results or dates.
- Do not invent numerical achievements.
- Do not automatically add unverified skills to the user's resume.
- Use follow-up questions when important information is missing.
- Allow users to leave optional information blank.
- Never treat an AI-generated suggestion as a verified personal fact.

If the user says they do not have work experience, create a fresher-oriented resume that emphasizes education, projects, internships and skills instead.

## 6. AI Resume Generation

Create a dedicated resume-generation service using the Anthropic Claude API.

The AI must generate a resume from the user's confirmed information, target job and optional job description.

### AI responsibilities

The AI should:

1. Convert natural-language answers into structured resume data.
2. Ask relevant follow-up questions.
3. Write a concise professional summary.
4. Organize skills into appropriate categories.
5. Rewrite project descriptions clearly.
6. Improve work-experience bullet points.
7. Emphasize relevant, verified achievements.
8. Tailor the wording to the target job description.
9. Use appropriate industry terminology.
10. Maintain professional grammar and consistent formatting.
11. Avoid unnecessary repetition.
12. Identify missing information that could improve the resume.
13. Return structured output that the frontend can reliably render.

### Structured response

Require the AI to return valid structured JSON matching a defined schema.

Example:

```json
{
  "targetRole": "Junior Data Engineer",
  "professionalSummary": "A concise summary based on verified information.",
  "skills": [
    {
      "category": "Cloud",
      "items": ["Amazon S3", "AWS Glue"]
    }
  ],
  "experience": [],
  "education": [],
  "projects": [],
  "certifications": [],
  "missingInformation": []
}
```

The example is illustrative. Define a complete schema covering all supported resume sections and validate the model output on the backend before returning it to the frontend.

Handle malformed JSON, missing fields, truncated responses and provider errors safely.

Do not assume every model response is valid JSON just because JSON was requested.

### Resume writing rules

- Use action-oriented language.
- Prefer concise, meaningful bullet points.
- Keep the resume easy to scan.
- Prioritize relevance to the target role.
- Preserve factual accuracy.
- Use measurable results only when provided by the user.
- Do not add keywords in a misleading manner.
- Do not claim that the resume is guaranteed to pass an ATS.
- Allow the user to review every AI-generated claim.

### Job description analysis

If the user supplies a job description, analyze:

- Required skills.
- Preferred skills.
- Main responsibilities.
- Experience requirements.
- Education requirements.
- Relevant keywords.
- Gaps between the job description and the user's confirmed profile.

Display a helpful summary of matching skills and missing or unverified requirements.

Do not change the user's actual qualifications to match the job description.

- Render the current edited resume, not the original AI-generated version.
- Preserve the selected template and supported formatting.
- Include all visible resume sections.
- Support one-page and multi-page resumes.
- Keep text selectable when using a text-based PDF generation approach.
- Preserve links when supported.

## 10. Backend API Endpoints

Implement REST API endpoints such as the following.

### General

- `GET /api/health` — check backend status.
- `GET /api/config/status` — report whether the AI service is configured without revealing credentials.

### Resume AI

- `POST /api/ai/interview` — process the user's answer and generate relevant follow-up questions.
- `POST /api/ai/generate-resume` — generate a structured resume from confirmed information.
- `POST /api/ai/improve-section` — improve a selected resume section.
- `POST /api/ai/analyze-job` — analyze a supplied job description.
- `POST /api/ai/suggest-improvements` — return recommendations based on the current resume and target role.

### Usage dashboard

- `GET /api/usage/status` — report usage data availability and its scope.
- `GET /api/usage/summary` — return available aggregate usage metrics.
- `GET /api/usage/details` — return detailed or time-bucketed usage when supported.

Validate all incoming requests and return consistent error responses.

Apply sensible input-size limits to job descriptions, resume content and chat messages.

Use request timeouts, rate limiting and appropriate HTTP status codes.

Do not expose internal stack traces, credentials or raw authorization headers to the browser.

## 12. AI API Key Usage Dashboard

Add an **AI API Usage** navigation item to the application.

When the user clicks it, display a dedicated dashboard for usage associated with the AI configuration used by this application.

The dashboard must distinguish usage made by this application from any broader Anthropic organization or project usage.

### A. Usage tracking

Track application requests made through the configured `AI_API_KEY`.

Record appropriate metadata, including:

- Timestamp.
- Model name.
- Feature used.
- Input tokens.
- Output tokens.
- Total tokens, where calculable.
- Request status.
- Request duration.
- Error category, when applicable.

Use token counts returned by Anthropic responses when available.

Do not store complete API keys, authorization headers, full prompts or unnecessary personal resume information in the usage log.

If token counts are unavailable for a failed request, mark them unavailable rather than inventing values.

Keep application-tracked usage separate from development usage and any unrelated API calls made outside this application. Never combine these figures without a clearly defined and valid calculation.

### B. Dashboard metrics

Show the following when reliable data is available:

1. Total input tokens.
2. Total output tokens.
3. Total tokens.
4. Total API requests.
5. Successful requests.
6. Failed requests.
7. Model usage breakdown.
8. Usage by feature, such as resume generation or section improvement.
9. Usage period.
10. Last-updated timestamp.
11. Provider-reported or estimated cost, when supported.

Use summary cards, a usage chart and a detailed table.

### C. Usage filters

Where supported by the available data, provide:

- Today.
- Last 7 days.
- Last 30 days.
- Custom date range.
- Model filter.
- Feature filter.

The detail table should include timestamp or reporting period, model, feature, input tokens, output tokens, total tokens, request status and cost where available.

Include pagination or sensible limits when displaying a large number of records.

### D. Anthropic organization Usage & Cost API

The supplied `.env.example` documents optional Anthropic Admin API usage reporting.

When `AI_USAGE_API_ENABLED=true`, use the documented Anthropic Usage & Cost API endpoints and the separately configured `AI_USAGE_API_KEY`, subject to the required permissions.

The template identifies these endpoints:

- `GET /v1/organizations/usage_report/messages`
- `GET /v1/organizations/cost_report`

Use the configured `AI_USAGE_BASE_URL` and follow the current official Anthropic API documentation for authentication, query parameters, pagination and response formats.

Important:

- The regular `AI_API_KEY` is for model requests.
- The Admin API credential is separate and optional.
- Organization-level usage is not automatically usage for the individual `AI_API_KEY`.
- Do not describe organization-wide usage as usage from this application.
- Do not assume the Admin API provides per-key reporting.
- If the requested scope is unsupported, explain the limitation and display the application-tracked usage instead.

Clearly label each data source:

**Application-tracked usage:** Requests recorded by this application using its configured API key.

**Anthropic-reported usage:** Usage returned by the official provider API, with its actual organization or project reporting scope stated clearly.

Do not add the two totals together unless their scopes are demonstrably non-overlapping and the calculation is valid.

### E. Cost and credit information

- Use provider-reported cost figures when available.
- If application cost is calculated locally, label it as an estimate and document the pricing assumptions.
- Do not hardcode unsupported prices or fabricate spending.
- Display remaining credit only when a reliable basis exists.
- If `AI_CREDIT_TOTAL` and `AI_CREDIT_START` are configured, show an appropriately labelled estimate based on the supported cost data since that date.
- Do not represent a calculated estimate as a live Anthropic account balance.
- If cost, balance or quota is unavailable, state that it is not provided by the configured API.

If the user has a project spending limit configured, display a warning as the tracked estimated usage approaches that limit. Keep this separate from Anthropic's actual account quota.

### F. Dashboard access control

Follow the supplied `USAGE_LOCALHOST_ONLY=true` setting.

For the initial local prototype, restrict usage endpoints to localhost when this setting is enabled.

Do not treat localhost restrictions as sufficient protection for a publicly deployed application. Document the need for proper authentication and authorization before public deployment.

Never return the full value of either API key to the frontend.
